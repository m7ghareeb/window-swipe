# Developer guide

How to work on Window Swipe: setting up, how the code is organised, testing and the build
tools. For the contribution process (forks, branches, pull requests), see
[CONTRIBUTING.md](../CONTRIBUTING.md). For releases, see [RELEASING.md](RELEASING.md).

## Setup

You need Cinnamon 6.6 with Touchégg, a touchpad, `git`, and for the build tools `python3`,
`python3-pil` and `zip`.

```sh
git clone https://github.com/<your-username>/window-swipe.git
cd window-swipe
git checkout -b fix/short-description
```

To run your working copy, copy the extension folder over the installed one:

```sh
mkdir -p ~/.local/share/cinnamon/extensions/window-swipe@ghareeb
cp window-swipe@ghareeb/* ~/.local/share/cinnamon/extensions/window-swipe@ghareeb/
```

If you use Window Swipe day to day, keep a copy of your installed version first so you can go
back to it. Then load the new code in one of these ways:

- **Looking Glass:** press **Alt+F2**, type `lg`, press **Enter**. On the **Extensions** tab,
  right-click **Window Swipe** and choose **Reload Code**.
- **Restart Cinnamon:** press **Ctrl+Alt+Esc**. Your windows stay open.

Enable the extension in **System Settings → Extensions** if it isn't enabled yet, and set up
gestures as described in the [installation guide](installation.md#set-up-gestures-one-time).

## How it works

`extension.js` is commented throughout; these are the main pieces.

- **Taking over swipes.** Cinnamon's gesture manager creates one action object per gesture with
  `imports.ui.gestures.actions.make_action()`. `enable()` replaces that function with
  `patchedMakeAction`, which returns Window Swipe's own action for horizontal three- and
  four-finger touchpad swipes and calls Cinnamon's original for every other gesture.
  `disable()` puts the original back. Cinnamon only creates actions for gestures that have one
  configured, which is why the gesture setup step is needed.
- **Which windows, in which order.** `isEligible` decides which windows take part,
  `eligibleWindows` sorts them (Plank dock order via `dockLaunchers` and `dockRank`, or opening
  order), and `startWindow` finds the window a swipe starts from.
- **The slide.** `SlideSession` draws the windows as compositor clones in an overlay, so real
  windows never move. It follows the fingers, decides at release whether to switch (the
  `FLICK_PROFILES` table), and glides to rest with a velocity-matched curve (the
  `GLIDE_PROFILES` table). A swipe that starts during a glide takes over the moving windows.
  Focus changes only once a switch is committed.
- **Settings.** `loadSettings` binds the settings window's values; `applySetting` validates them
  and falls back to the defaults for invalid values.
- **Clean-up.** Everything created by a slide is released when it ends and in `disable()`.

Touchégg fixes a swipe's direction when it starts and never reports progress below zero. This is
why a single swipe can't continue past the starting window to the other side; it is a property
of the input, not something the extension can change.

## Debugging

- Log messages start with `[window-swipe]`. Read them in Looking Glass (**Logs** tab) or with
  `grep -i window-swipe ~/.xsession-errors`.
- While the extension is enabled, `globalThis.__windowSwipe` offers diagnostics. Type these
  into the command line at the bottom of Looking Glass; the answer appears on the **Results**
  tab:
  - `__windowSwipe.settings()`: current animation, sensitivity, order and fingers;
  - `__windowSwipe.order()`: the window order (WM classes) on the primary monitor;
  - `__windowSwipe.lastStats`: measurements of the last swipe;
  - `__windowSwipe.swipes()`: recent swipes, kept in memory only (up to 500).

  `__windowSwipe.setSetting(key, value)` changes a setting the same way the settings window
  does, which is useful for comparing profiles quickly.

## Testing

There are no automated tests for the gesture itself: it needs a real touchpad. Please go through
the checklist in [CONTRIBUTING.md](../CONTRIBUTING.md#testing-checklist) before opening a pull
request, and watch the log for errors while you test.

## Tools and checks

| Command | What it does |
|---|---|
| `node --check window-swipe@ghareeb/extension.js` | Checks the JavaScript syntax |
| `python3 tools/check-metadata.py` | Checks `metadata.json`, `settings-schema.json` and that the version matches the newest `CHANGELOG.md` entry |
| `tools/build-release.sh [revision]` | Builds the release zip and `SHA256SUMS` into `dist/v<version>/` from a committed revision (default `HEAD`). The same revision always gives a byte-identical zip |
| `tools/build-spices.sh [revision] [validate-spice]` | Assembles the Cinnamon Spices folder in `dist/spices/`, and runs the official validator if you give its path |
| `python3 tools/make_icon.py` | Redraws `icon.png` |
| `python3 tools/media/render_demo.py <dir>` | Renders the README illustration (`demo.gif`, `slide.png`) offline from the extension's release logic; needs `python3-pil` and the Noto Sans and DejaVu fonts |

The build scripts read from Git, not from your working files, so commit your changes before
building.

**Continuous integration.** The `Validate` workflow runs on every pull request and every push to
`main`. It runs the syntax and metadata checks, assembles the Spices folder and checks it with
the official `validate-spice` script (pinned to a reviewed version and verified by checksum),
and builds the release zip twice to confirm it's reproducible. It has read-only access and uses
no secrets. For pull requests from outside contributors, the maintainer approves each run
before it starts.

## Code style

- 4-space indentation, `const` and `let`, and comments that explain *why*.
- JavaScript supported by Cinnamon's engine (SpiderMonkey 102 or newer).
- Release everything you create in `disable()`: timers, signal handlers, actors.
- No network access, no external programs, no files written outside Cinnamon's settings, and no
  blocking work during a swipe.
- `metadata.json` must stay ASCII-only for Cinnamon Spices.
- `.editorconfig` sets indentation and line endings for most editors.
